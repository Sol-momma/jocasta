## この記事でわかること

- たくさんの環境にシステムを出すときに、何が困るのか
- 「バージョンを決める」と「どこに出したか記録する」を分けて考える理由
- そのためによく使われる道具（changesets、release-please、GitHub Environments など）の役割
- 手作業のデプロイから、少しずつ自動化していく順番

**対象読者**：Git とGitHubを少し触ったことがある人。「リリース管理」や「CI/CD」という言葉ははじめて、という人を想定しています。

## 結論

- 「バージョンを決める仕組み」と「どこに出したかを記録する仕組み」を分けて考えます。
- バージョンは道具を使って番号を付け、その番号のコードをそのまま本番などに出します。
- どこに出したかの記録は、GitHub や Azure DevOps の「Environments」という機能に任せます。
- 手作業でコマンドを打つやり方だと、この記録が残りません。ここが一番の問題です。

## そもそも、何が困るのか

まず言葉をそろえます。

- **環境**：システムが動いている場所のことです。開発用、テスト用、本番用などがあります。同じシステムでも、置き場所ごとに別の「環境」と呼びます。
- **デプロイ**：書いたプログラムを、環境に置いて動く状態にする作業です。
- **リリース**：新しいバージョンを使える状態にすることです。デプロイとほぼ同じ意味で使われることもあります。

ここで、環境が8つあると考えてみます。さらに、利用者ごとにリリースする時期や、使うクラウドの部品（サーバーやデータベース）が少しずつ違うとします。

この状態で、毎回手でコマンドを打ってデプロイしていると、次のようなことが起きます。

- 「3番目の環境に、今どのバージョンが入っている？」と聞かれても、すぐに答えられない
- 不具合が出たとき、どの変更が原因かわからない
- 同じ手順のつもりでも、人によってコマンドのオプションが少しずつ違う

> **コラム：モノレポとは**
> モノレポは、複数のプログラム（たとえば画面のプログラムとサーバーのプログラム）を、1つのリポジトリ（Gitでコードを置いておく場所）にまとめて管理するやり方です。コードを一か所で見られるのが利点です。一方で、「画面はバージョン2、サーバーはバージョン5」のように、中の部品ごとにバージョンが分かれるので、管理が少し複雑になります。

## 1. バージョンを決める道具：changesets と release-please

**バージョン**は、「この時点のコード」に付ける番号です。`1.4.0` のような形がよく使われます。

> **コラム：バージョン番号の読み方**
> `1.4.0` は左から「メジャー.マイナー.パッチ」と読みます。
> - パッチ（右）：不具合を直しただけ
> - マイナー（真ん中）：機能を足したが、今までの使い方はそのまま使える
> - メジャー（左）：今までの使い方が変わる
> この決まりを「セマンティックバージョニング」と呼びます。

番号を手で付けると、付け忘れや付け間違いが起きます。そこで道具に任せます。代表的なのが次の2つです。

| | changesets | release-please |
|---|---|---|
| 番号の決め方 | 変更を出すたびに、開発者が「この部品はパッチで上げる」と書いた小さなファイルを一緒に出す | コミットメッセージの書き方（`feat:` なら機能追加、`fix:` なら修正）から自動で決める |
| モノレポで使えるか | 使える。お互いに依存している部品をまとめて更新できる | 使える。「どの部品が今何番か」を書いた表（manifest というファイル）で管理する |
| 合いそうなチーム | コミットメッセージの書き方をそろえるのが難しいチーム | 書き方をそろえられるチーム |

どちらを使っても、最後には「`api@1.4.0` という名前＝このコード」という目印が残ります。この目印を**タグ**と呼びます。タグがあれば、あとから「1.4.0 のときのコード」をいつでも取り出せます。

## 2. ビルドを速くする道具：Nx と Turborepo

**ビルド**は、書いたプログラムを動かせる形にまとめる作業です。

Nx と Turborepo は、「変更があった部品だけビルドする」「一度ビルドした結果を再利用する」ための道具です。バージョン管理の道具ではありません。部品が増えてビルドが遅くなったときに役立ちます。

最初から入れる必要はありません。「ビルドが遅い」と感じてからで十分です。なお、Nx には `nx release` というバージョン管理の機能もあります（未確認：今どこまでできるかは公式ドキュメントで要確認）。

## 3. どこに出したかを記録する：Environments

ここが一番大事なところです。

GitHub にも Azure DevOps にも、「Environments（環境）」という機能があります。これは、**デプロイするたびに「どの環境に、いつ、どのコードを出したか」を自動で記録してくれる機能**です。

たとえるなら、宅配便の配達記録のようなものです。荷物（コード）を、どの住所（環境）に、いつ届けたかが一覧で残ります。実際には、デプロイ用の自動処理の設定に環境の名前を1行書くと、その処理が動いたときに記録が作られます。

### GitHub の場合

GitHub Actions は、GitHub 上で決まった作業を自動で動かす仕組みです。その設定ファイルに `environment: env-a` のように環境の名前を書きます。すると、リポジトリのトップページに、環境ごとのデプロイ履歴が表示されます。

ほかにも、次のことができます。

- 誰かが承認するまで、デプロイを止めておく
- 決まったブランチからしかデプロイできないようにする
- 環境ごとに別のパスワードや鍵（シークレット）を持たせる

環境が8つなら、Environment も8つ作るのが一番わかりやすい形です。

### Azure DevOps の場合

Azure Pipelines（Azure DevOps の自動処理の仕組み）でも、設定に `environment` を書くと、環境ごとの履歴が残ります。そのとき新しく入った変更や作業項目も追えます。公式ドキュメントには「中身が空の Environment を作って指定するだけでも、履歴は残せる」と書かれています。

### 全体の流れ

1. 道具（release-please など）がタグを作る
2. デプロイ用の自動処理に、「どのタグを」「どの環境に」出すかを指定して動かす
3. 環境ごとの違い（使うサーバーの名前、オンにする機能など）は、`environments/環境名.json` のような設定ファイルに書いておき、そこから読む
4. 結果が Environments の履歴に残る

これで「3番目の環境に今何が入っている？」と聞かれても、画面を見れば答えられます。

## 4. 手作業から少しずつ移る

いきなり全部を自動にしなくて大丈夫です。おすすめの順番はこうです。

1. 今手で打っているコマンドを、そのままスクリプト（コマンドを並べたファイル）にして、リポジトリに置く
2. そのスクリプトを GitHub Actions や Azure Pipelines から、ボタンを押して動かせるようにする。設定に `environment` を書く
3. この時点で、デプロイの履歴が残り始める。効果の大半はここで得られる
4. 慣れてきたら、タグ作成やテストも自動にしていく

自動処理から Azure にログインするときは、長く使える鍵をそのまま保存するより、OpenID Connect（OIDC）という方式のほうが安全です。OIDC は、毎回その場かぎりの短い許可証を発行してもらう仕組みです（未確認：チームの方針や権限によっては使えない場合があります）。

## 用語集

| 用語 | 意味 |
|---|---|
| 環境 | システムが動いている場所。開発用・テスト用・本番用など |
| デプロイ | プログラムを環境に置いて、動く状態にする作業 |
| リリース | 新しいバージョンを使える状態にすること |
| リポジトリ | Git でコードと変更履歴を置いておく場所 |
| モノレポ | 複数のプログラムを1つのリポジトリで管理するやり方 |
| バージョン | ある時点のコードに付ける番号（例：1.4.0） |
| タグ | 特定の時点のコードに付ける目印。バージョン番号を付けることが多い |
| コミットメッセージ | コードの変更を保存するときに書く、短い説明文 |
| ビルド | プログラムを動かせる形にまとめる作業 |
| CI/CD | テストやデプロイを自動で行う仕組みの総称 |
| GitHub Actions | GitHub 上で作業を自動で動かす仕組み |
| Azure Pipelines | Azure DevOps 上で作業を自動で動かす仕組み |
| シークレット | パスワードや鍵など、人に見せてはいけない値 |
| OIDC | 毎回その場かぎりの許可証でログインする方式 |
